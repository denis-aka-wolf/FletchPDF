# Архитектура FletchPDF

## 1. Принципы

FletchPDF является локальным desktop-приложением. Flutter отвечает за интерфейс и пользовательские сценарии. Работа с PDF делегируется специализированным движкам через адаптеры.

Запрещённые архитектурные зависимости:
- UI не запускает CLI напрямую.
- UI не знает о конкретных аргументах QPDF, Ghostscript или Tesseract.
- Движки не управляют Flutter-навигацией и состоянием экранов.
- Для выполнения операций не требуется локальный HTTP-сервер.

## 2. Слои

### Presentation
Экраны, виджеты, навигация, диалоги и локальное состояние интерфейса.

### Application
Сценарии пользователя: открыть документ, объединить PDF, разделить документ по группам страниц, извлечь страницы, организовать страницы, конвертировать, выполнить OCR. Объединение, разделение и организация страниц используют PdfDocument API из pdfrx/PDFium. Здесь управляются очередь, прогресс, отмена и результаты.

### Domain
Модели документов, операций, ошибок и контракты PDF-движков. Domain не зависит от Flutter UI и конкретного CLI.

### Infrastructure
Реализации контрактов: pdfrx/PDFium, QPDF, MuPDF, Ghostscript, Tesseract, LibreOffice и файловая система.

## 3. Движки

| Движок | Назначение | Статус |
|---|---|---|
| pdfrx / PDFium | Просмотр, рендеринг, объединение, разделение, извлечение и визуальная организация страниц PDF | Подключён; просмотр, объединение, разделение по группам и извлечение выбранных страниц и визуальная организация страниц (перестановка, удаление, дублирование, поворот) реализованы |
| QPDF | Структурные операции, split, шифрование и дополнительные проверки | Адаптер в разработке, бинарник не поставляется; объединение выполняется через PDFium |
| MuPDF | Расширенная обработка и преобразования | Требует отдельной оценки |
| Ghostscript | Конвертация и оптимизация | Требует отдельной оценки |
| Tesseract | OCR | Требует отдельной оценки |
| LibreOffice | Office → PDF | Требует отдельной оценки |
| veraPDF | Валидация PDF/A | Требует отдельной оценки |

Каждый движок должен предоставлять проверку доступности и версии. Отсутствие необязательного движка не должно ломать запуск приложения.

## 4. Выполнение операций

Каждая операция должна:
1. Проверять входные файлы и параметры.
2. Проверять доступность нужного движка.
3. Выбирать выходной путь, не перезаписывая исходник без явного подтверждения.
4. Запускаться асинхронно.
5. Возвращать структурированный результат или диагностируемую ошибку.
6. Записывать технический журнал без содержимого документов и секретных данных.

Для CLI использовать запуск процесса с массивом аргументов и `runInShell: false`. Не собирать shell-команду конкатенацией пользовательского ввода.

## 5. Хранение

Настройки и история хранятся локально. Исходные PDF не копируются в каталог приложения автоматически. Временные файлы должны удаляться после завершения операции или аварийного восстановления.

## 6. Лицензии и поставка

Для каждой версии релиза формируется SBOM/реестр компонентов:
- имя и точная версия;
- upstream URL;
- лицензия и текст лицензии;
- источник бинарного файла;
- SHA-256;
- целевые платформы и архитектуры;
- модификации и патчи;
- способ включения в дистрибутив.

AGPL-компоненты требуют отдельного анализа обязательств при распространении. Отдельный процесс для CLI сам по себе не является гарантией отсутствия copyleft-обязательств.
